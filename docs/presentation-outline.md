# Presentation outline

Ten slides for approximately 10–12 minutes, including the short live demo. Use the figures supplied in `docs/figures` and `results/experiment.png`. Bracketed references correspond to the report. All reported experiment numbers are from the saved run; no slide requires a new benchmark during the presentation.

## Slide 1 — Our question and demonstration

- Exploring parallel and distributed computing, COSC 451.
- Count whole-word occurrences using multiple threads.
- Check correctness, show coordination, then measure worker-count effects.

**Speaker notes:** We chose a result that everyone can check by hand. Our aim is to explain which worker does what and whether the execution mechanism actually helps. The main program uses threads; processes are a secondary comparison.

## Slide 2 — Parallel and distributed can coexist

- Parallel: multiple compute resources work simultaneously on a problem.
- Distributed: cooperating components run on networked machines with separate memory.
- Examples: Blender GPU rendering [2]; Google's historical MapReduce [3].
- A cluster can use local parallel workers inside each node [1].

**Speaker notes:** These terms are not mutually exclusive. Also distinguish concurrency from simultaneous execution: standard CPython threads can have overlapping lifetimes without executing their Python loops on different cores at once.

## Slide 3 — Work division and communication

- Show `figures/parallel.png` and `figures/distributed.png` side by side.
- Local threads share the input and publish partial counts.
- Distributed workers need messages and task identities.
- Local process pools on this laptop are not networked distribution.

**Speaker notes:** Follow arrows from assignment to worker to result. We implemented the first design. The distributed diagram is a conceptual extension and illustrates why retries and duplicate replies need explicit handling.

## Slide 4 — How our counter defines and splits work

- Token = letters/digits/underscores; punctuation separates tokens.
- `the` matches `the,`, not `other`, `the2`, or `the_the`.
- Main reads UTF-8; workers receive adjacent complete-line ranges.
- Each line belongs to exactly one worker; empty ranges are valid.

**Speaker notes:** Point to `partition_lines` and `count_lines`. A final newline is optional. Whole lines make the boundary argument simple but can produce load imbalance if line lengths vary greatly. We read the full file into memory.

## Slide 5 — Trace and hand-check

- Show `data/sample.txt`: exact lowercase count is **7**.
- Three workers: lines 1–2 → 2; lines 3–4 → 3; lines 5–6 → 2.
- Run the three-thread trace and point to name, ID, range, size, timestamps.
- Main combines **2 + 3 + 2 = 7** after completion.

**Speaker notes:** Use demo-script steps 2–4. Trace rows are printed after joins in chunk order. Times and IDs vary. Our recorded tiny task ran its worker intervals successively, which is not evidence of CPU parallelism. Case-insensitive mode has two extra matches, totaling nine.

## Slide 6 — Synchronization and a visible race

- `lock`: one shared-counter update per worker inside a critical section.
- `slots`: one writer per output slot; main sums after joins.
- Controlled race: expected **400**, unsafe **100**, locked **400**.
- Barriers and a forced yield deliberately expose the stale-read interleaving.

**Speaker notes:** Run the slots command and race command. Explain read-zero/read-zero/write-one/write-one. The test does not establish how often ordinary `+=` fails. Slots avoid our combine mutex, but joining still synchronizes; this is not a formal lock-free algorithm.

## Slide 7 — Verification and prediction

- **29 tests passed** in the captured run.
- Tests cover boundaries, empty input, case, substrings, Unicode, excess workers, and process agreement.
- Pre-run prediction: no useful thread scaling; processes may help after overhead.
- Fixed 50 MiB input; expected count **2,759,412**.

**Speaker notes:** Show the saved test log or run the tests. The large expected count is three matches per generated line times 919,804 lines, not an answer generated by the implementation being tested. The prediction is saved separately and copied into metadata.

## Slide 8 — Experiment method and results

- i7-1185G7: 4 physical cores, 8 logical processors; Windows 11; CPython 3.13.15.
- Workers: 1, 2, 4, 8, 16; one warm-up plus three repetitions per setting/backend.
- Read excluded; dispatch, startup, process transfer, scan, reduction, shutdown included.
- Show `results/experiment.png`; error bars are sample standard deviation.

**Speaker notes:** All 40 counts were correct, including warm-ups. The one-thread mean is 4.8630 s. Four threads average 4.7495 s, essentially the same given the spread. Eight processes average 2.0059 s, the lowest observed mean, or 2.424× against one thread. Do not interpret the small four-versus-eight-process difference as proof of an optimum.

## Slide 9 — Why the results differ

- GIL-enabled threads share one Python bytecode execution opportunity [5].
- Separate processes have separate interpreters [7], [8].
- Startup, serialization, scheduling, and shared hardware resources cost time.
- Large timing variation limits precision; no free-threaded build was benchmarked.

**Speaker notes:** The design and timings support a process advantage for this workload, not a general claim that processes always win. There is no regex or `str.count` shortcut in the timed scanner. We did not measure CPU utilization or context switches, so identify these as explanations consistent with the evidence.

## Slide 10 — Conclusions and sources

- Correct partitioning and ownership make the answer explainable.
- Synchronization protects shared updates; separate slots simplify combination.
- More threads did not provide useful scaling here; processes gave a measured improvement.
- Distributed designs additionally need communication and failure handling.
- Sources: LLNL [1], Blender [2], Dean and Ghemawat [3], OSTEP [4], [6], [9], Python docs [5], [7], [8]. Full references are in the report.

**Speaker notes:** Finish by separating three claims: our counts are verified, our race is deliberately reproducible, and our speedup results apply to this measured setup.
